Processor evidence · what step 5 will extend

What the Pi’s processor is doing

A Raspberry Pi 4 has four CPU cores and no neural accelerator. Camera decoding, image motion, the detector, the IMU thread, scene memory and file writing all share them. This page gathers what has actually been measured, so you can see where time and cores go before deciding what to optimize or move to the FPGA.

How to read these numbers
CPU %100% = one core fully busy. The Pi has four, so a process can show up to 400%. “System busy” uses the whole chip as 100%.
Median, p95, maxHalf the samples are below the median; 95% are below p95. The max is the single worst case, often the one users notice.
Rate versus timeHz is updates per second. Milliseconds measure how long one step takes or how old a result is.
One run, one sceneEach value comes from a specific run with written conditions. Different runs are not interchangeable and are labelled.

2 · How often each part runs

Each worker runs at its own rate measured

Why the rates differ

The workers are independent threads. Each takes the newest camera frame when it is ready instead of queueing every frame. Motion analysis needs about 31 ms per frame and finished 26 of every 30 frames; the 1,203 it skipped in 300 s are frames it never looked at, not failed estimates. The detector is deliberately throttled to 2 Hz because one inference takes about 226 ms of compute. The camera itself can do more: a 1280×720 MJPEG stream ran at about 118.7 fps in a separate capture test.

5 · Medians hide stalls

A 14 ms write that sometimes takes 3.6 s measured

Saving evidence images to the microSD card usually took about 14 ms, but rare writes took seconds. When the scene worker did that saving itself, recognition stopped while it waited. The fix was structural: a separate writer thread with a small bounded queue, so recognition never waits for the card. A later single-pair experiment moved only the profiler’s own log from the card into RAM: the worst stalls in the application’s writes fell sharply, at the cost of about 48 MiB more profiler memory (20 MiB → 68 MiB RSS).

What this does not show: that the microSD card is defective, or that application writes are solved. One pair supports “less competition for the same storage”; causes inside the kernel and card remain unproven. See the RAM observer result and kernel I/O trace.
6 · Compute intensity

How hard the detector works the cores derived

1.12 billionmultiply-accumulates per detection (layer arithmetic, heads excluded)
226 msmedian detector compute on the Pi (measured)
≈4.9 billion/smultiply-accumulates per second achieved, a lower bound

Dividing the operation count by the measured time gives the throughput the CPU actually reached with two OpenCV threads. It is a lower bound because the 226 ms also includes resizing, normalization and decoding the boxes. The detector model page shows which layers this work comes from: 92% is in 1×1 “pointwise” convolutions, which are matrix multiplications, the classic target for SIMD and FPGA multiply arrays.

7 · Not measured yet

The gaps step 5 must fill

  • Per-stage CPU inside the integrated program: the numbers above come from different runs and configurations.
  • Hardware counters: instructions per cycle, cache misses and memory bandwidth (Linux perf), which show whether a stage is limited by arithmetic or by memory.
  • Energy: needs a power meter; CPU time is not energy.
  • Camera-to-screen latency, including SSH and browser delay.
  • Thermal steady state with a recorded power supply and ambient temperature.
  • Depth-network cost (step 4), in float and int8.
